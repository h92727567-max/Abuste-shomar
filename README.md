# ابوسطه‌شمار — Phase 1 + Phase 2

## Phase 1

این پکیج شامل **Phase 1** از پرامپت اصلی است:

- ساخت اسکلت پروژه Kotlin + Android Studio
- `MainActivity` مبتنی بر Jetpack Compose
- تم Material 3 (`Theme.kt`, `Color.kt`, `Type.kt`)
- اجباری کردن جهت راست‌به‌چپ (RTL) در کل برنامه، مستقل از زبان سیستم
- صفحه اصلی اولیه (`HomeScreen.kt`) با:
  - عنوان «ابوسطه‌شمار»
  - دو کارت گروه (امتیاز هر دو فعلاً ثابت روی صفر)
  - چهار دکمه: شروع بازی جدید / ادامه بازی (غیرفعال چون هنوز بازی ذخیره‌شده‌ای وجود ندارد) / تاریخچه بازی‌ها / تنظیمات

هیچ منطق بازی، Database، یا Navigation واقعی در این فاز پیاده‌سازی نشده — طبق دستور، این‌ها در فازهای بعدی (2 به بعد) اضافه می‌شوند. دکمه‌ها فعلاً callbackهای خالی دارند تا در فاز Navigation به صفحات واقعی وصل شوند.

## Phase 2 — صفحه بازی

**فایل‌های جدید:**

```
app/src/main/java/com/abusteh/shomar/
├── domain/model/Game.kt          ← مدل ساده در حافظه (بدون Database)
├── viewmodel/GameViewModel.kt    ← وضعیت بازی (نام گروه‌ها، امتیاز)
└── ui/screens/
    ├── NewGameScreen.kt          ← دریافت نام دو گروه (بخش ۵ مشخصات)
    └── GameScreen.kt             ← صفحه بازی (بخش ۶ مشخصات)
```

`MainActivity.kt` به‌روزرسانی شد و اکنون از **Navigation Compose** برای رفتن بین
سه صفحه استفاده می‌کند: صفحه اصلی ← شروع بازی جدید ← صفحه بازی.
`GameViewModel` در سطح Activity ساخته می‌شود تا وضعیت بازی بین صفحه‌ها مشترک بماند
(هنوز ذخیره‌سازی دائمی ندارد — Room در Phase 7 اضافه می‌شود).

**آنچه در این فاز پیاده‌سازی شده:**
- ورود نام گروه اول و دوم (با نام‌های پیش‌فرض «گروه ۱» / «گروه ۲» در صورت خالی بودن)
- صفحه بازی با دو کارت گروه (نام + امتیاز، شروع از ۰-۰)
- نمایش «دور فعلی» (شروع از ۱)، «آخرین دور ثبت‌شده» (فعلاً «هنوز ثبت نشده»)، و «گروه پیشتاز» (یا «مساوی»)
- دکمه‌های «ثبت دور جدید»، «لغو آخرین دور»، «مشاهده تاریخچه» — فقط از نظر ظاهری آماده‌اند؛ عملکرد واقعی به‌ترتیب در Phase 4، Phase 6 و Phase 5 اضافه می‌شود (طبق برنامه فازبندی، callback خالی دارند)

**آنچه در این فاز پیاده‌سازی نشده (عمداً):**
- منطق واقعی امتیازدهی/جریمه/کوت (Phase 3)
- ثبت دور واقعی (Phase 4)
- تاریخچه دورها (Phase 5)
- Undo واقعی (Phase 6)
- Room Database (Phase 7)

### نحوه تست Phase 2

1. برنامه را اجرا کنید.
2. «شروع بازی جدید» را بزنید.
3. یک یا هر دو نام گروه را خالی بگذارید یا پر کنید، سپس «شروع بازی» را بزنید.
4. بررسی کنید:
   - اگر نامی خالی بود، نام پیش‌فرض («گروه ۱» یا «گروه ۲») در صفحه بازی نمایش داده شود.
   - هر دو امتیاز ۰ باشند.
   - «دور فعلی» برابر ۱ باشد.
   - «آخرین دور ثبت‌شده» → «هنوز ثبت نشده».
   - «گروه پیشتاز» → «مساوی» (چون امتیازها برابرند).
   - دکمه‌های «ثبت دور جدید»، «لغو آخرین دور»، «مشاهده تاریخچه» قابل لمس باشند ولی فعلاً کاری انجام ندهند (طبیعی است).
5. با دکمه Back گوشی به صفحه اصلی برگردید و دوباره «شروع بازی جدید» را امتحان کنید تا مطمئن شوید state درست ریست/جایگزین می‌شود.

## Phase 3 — موتور قوانین

**فایل‌های جدید:**

```
app/src/main/java/com/abusteh/shomar/domain/rules/
├── AbusteRules.kt      ← قوانین خام بازی (مستقل از Android)
└── ScoringEngine.kt    ← واسط بین ViewModel و AbusteRules، اعمال نتیجه روی Game

app/src/test/java/com/abusteh/shomar/domain/rules/
├── AbusteRulesTest.kt      ← ۱۱ تست Unit
└── ScoringEngineTest.kt    ← ۹ تست Unit
```

**قوانین پیاده‌سازی‌شده (تأییدشده توسط شما در گفتگو):**

| مورد | قانون |
|---|---|
| بازه مقدار خواندن (bid) | ۵ تا ۹ |
| موفق، بدون کوت | امتیاز = bid → به گروه خواننده |
| موفق، با کوت | امتیاز = ۲×bid → به گروه خواننده |
| ناموفق (کوت یا عادی، فرقی ندارد) | ۲×bid → به گروه **حریف** |
| امتیاز برد | ۶۲ یا بیشتر |

نکته مهم: کوت **فقط** روی حالت موفق اثر می‌گذارد (طبق تأیید صریح شما)؛ در حالت ناموفق نادیده گرفته می‌شود و قانون استاندارد جریمه (۲×bid به حریف) اجرا می‌شود.

**معماری (طبق بخش ۳۵ مشخصات):**

```
ViewModel → ScoringEngine → AbusteRules
```

`AbusteRules` هیچ وابستگی‌ای به Android یا حتی به مدل `Game` ندارد — فقط عدد می‌گیرد و عدد برمی‌گرداند (`RoundOutcome`). `ScoringEngine` این خروجی را روی `Game` واقعی (با دانستن اینکه خواننده گروه یک است یا دو) اعمال می‌کند و شماره دور را هم یک واحد بالا می‌برد.

در Android Studio: کلیک راست روی پوشه `app/src/test/java/...` → Run Tests، یا از ترمینال:

```
./gradlew test
```

نتیجه در:
```
app/build/reports/tests/testDebugUnitTest/index.html
```

### تست‌های نوشته‌شده (خلاصه)

- محدوده مجاز bid (۵ تا ۹) و رد مقادیر خارج از بازه (پرتاب Exception)
- موفق بدون کوت → امتیاز درست به خواننده
- موفق با کوت → دقیقاً ۲ برابر
- ناموفق → دقیقاً ۲ برابر به حریف، چه کوت باشد چه نباشد (نتیجه یکسان)
- تشخیص برنده دقیقاً در ۶۲ و بالاتر، و رفتار در حالت مرزی
- اعمال درست دلتای امتیاز بسته به اینکه خواننده گروه ۱ یا ۲ باشد
- افزایش شماره دور بعد از هر بار `applyRound`
- انباشت امتیاز در چند دور متوالی

**در این فاز عمداً پیاده‌سازی نشده:** اتصال این موتور به UI (Phase 4)، Dialog ثبت دور (Phase 4)، ذخیره تاریخچه دورها (Phase 5).

## Phase 4 — ثبت دور

**فایل‌های جدید:**

```
app/src/main/java/com/abusteh/shomar/ui/
├── components/
│   ├── ConfirmDialog.kt     ← Dialog تأیید عمومی (بخش ۱۱ و ۱۵)
│   └── OptionSelector.kt    ← ردیف انتخاب تک‌گزینه‌ای (گروه/مقدار/نتیجه/کوت)
└── screens/
    └── RoundScreen.kt       ← صفحه ثبت دور جدید (بخش ۷)
```

`GameViewModel.registerRound(...)` اضافه شد که فقط `ScoringEngine.applyRound(...)` را
صدا می‌زند و نتیجه را روی وضعیت بازی می‌نشاند — منطق امتیازدهی مستقیماً داخل
ViewModel یا UI نوشته نشده (طبق بخش ۳۵ مشخصات).

مسیر `round` به Navigation اضافه شد: دکمه «ثبت دور جدید» در `GameScreen` حالا
واقعاً به این صفحه می‌رود.

**جریان کامل ثبت دور:**

1. در صفحه بازی، «ثبت دور جدید» را بزنید.
2. گروه خواننده، مقدار خواندن (۵ تا ۹)، نتیجه (موفق/ناموفق) و کوت (خیر/بله، پیش‌فرض خیر) را انتخاب کنید.
3. دکمه «ثبت دور» تا وقتی گروه، مقدار و نتیجه انتخاب نشده باشند غیرفعال است (بخش ۲۲ — جلوگیری از ثبت ناقص).
4. با زدن «ثبت دور»، Dialog تأیید (بخش ۱۱) خلاصه دور را نشان می‌دهد: گروه خواننده، مقدار خواندن، نتیجه، کوت، و مقدار دقیق امتیاز/جریمه و اینکه به کدام گروه تعلق می‌گیرد.
5. «تأیید ثبت» → دور واقعاً از طریق `ScoringEngine` ثبت می‌شود، امتیازها فوراً به‌روزرسانی می‌شوند (بخش ۱۳) و به صفحه بازی برمی‌گردید.
6. «بازگشت» → فقط Dialog بسته می‌شود، فرم دست‌نخورده باقی می‌ماند.

**نکته درباره تنظیم «تأیید قبل از ثبت»:** طبق بخش ۱۱ مشخصات، این Dialog باید وابسته به یک تنظیم قابل‌غیرفعال‌سازی باشد. آن تنظیم بخشی از صفحه تنظیمات است که در **Phase 11** ساخته می‌شود؛ فعلاً Dialog همیشه نمایش داده می‌شود (این رفتار پیش‌فرض امن‌تری است).

**در این فاز عمداً پیاده‌سازی نشده:**
- ذخیره تاریخچه دورها (Phase 5) — دور ثبت می‌شود ولی جایی لاگ نمی‌شود، فقط امتیاز نهایی تغییر می‌کند
- Undo واقعی (Phase 6)
- تشخیص پایان بازی در ۶۲ امتیاز و صفحه برنده (Phase 9) — اگر امتیازی به ۶۲ برسد، فعلاً فقط عدد در کارت گروه بالا می‌رود و بازی متوقف نمی‌شود

### نحوه تست Phase 4

1. بازی جدید بسازید (مثلاً «گروه A» و «گروه B»).
2. «ثبت دور جدید» بزنید بدون انتخاب چیزی → دکمه «ثبت دور» باید غیرفعال باشد.
3. گروه A را به‌عنوان خواننده، مقدار ۷، نتیجه «موفق»، کوت «خیر» انتخاب کنید → «ثبت دور» را بزنید.
4. در Dialog باید ببینید: «امتیاز: ۷ برای گروه A». «تأیید ثبت» بزنید → امتیاز گروه A باید ۷ شود.
5. یک دور دیگر: گروه B خواننده، مقدار ۵، نتیجه «ناموفق»، کوت «خیر» → Dialog باید نشان دهد «جریمه: ۱۰ برای گروه A» (چون جریمه به حریف گروه B می‌رود) → بعد از تأیید، امتیاز گروه A باید ۱۷ شود (۷+۱۰).
6. یک دور با کوت: گروه A خواننده، مقدار ۶، موفق، کوت «بله» → Dialog باید «امتیاز: ۱۲ برای گروه A» نشان دهد.
7. یک دور ناموفق با کوت فعال: باید دقیقاً مثل ناموفق بدون کوت رفتار کند (۲×مقدار به حریف، بدون تغییر اضافه از کوت).
8. «بازگشت» در Dialog را امتحان کنید → فرم باید دست‌نخورده بماند و هیچ امتیازی تغییر نکند.

## Phase 5 — تاریخچه دورها

**فایل‌های جدید:**

```
app/src/main/java/com/abusteh/shomar/
├── domain/model/Round.kt         ← رکورد یک دور (بخش ۱۴ مشخصات)
└── ui/screens/HistoryScreen.kt   ← نمایش تاریخچه دورهای بازی جاری
```

**تغییرات مهم:**

- `ScoringEngine.applyRound(...)` اکنون به‌جای فقط `Game`، یک `RoundApplicationResult` (شامل بازی جدید + `RoundOutcome` خام) برمی‌گرداند تا لایه‌های بالاتر بدون فراخوانی مجدد قوانین، دقیقاً بدانند چقدر امتیاز/جریمه اعمال شد. تست‌های `ScoringEngineTest` با این تغییر هماهنگ شدند.
- `GameViewModel` اکنون یک `StateFlow<List<Round>>` هم دارد؛ هر بار `registerRound(...)` صدا زده شود، هم بازی به‌روزرسانی می‌شود و هم یک رکورد `Round` کامل (شماره دور، گروه خواننده، مقدار خواندن، نتیجه، کوت، امتیاز هر دو گروه قبل/بعد، مقدار اعمال‌شده) به تاریخچه اضافه می‌شود.
- دکمه «مشاهده تاریخچه» در `GameScreen` اکنون واقعاً به صفحه تاریخچه می‌رود (مسیر جدید `round_history`).
- «آخرین دور ثبت‌شده» در `GameScreen` دیگر ثابت نیست — خلاصه واقعی آخرین دور را نشان می‌دهد (مثلاً «گروه A - خواند ۷ - موفق»).

**نکته مهم درباره دو نوع «تاریخچه»:** طبق مشخصات دو تاریخچه متفاوت وجود دارد که نباید با هم اشتباه شوند:
- **تاریخچه دورهای بازی جاری** (بخش ۱۴) — همینی که در Phase 5 ساخته شد، از صفحه بازی در دسترس است.
- **تاریخچه بازی‌های قبلی** (بخش ۱۰) — لیست بازی‌های تمام‌شده، از صفحه اصلی در دسترس است؛ این یکی هنوز در Phase 10 ساخته می‌شود.

**در این فاز عمداً پیاده‌سازی نشده:**
- ذخیره دائمی تاریخچه (Room — Phase 7): با بستن برنامه، تاریخچه از بین می‌رود.
- Undo واقعی که رکورد تاریخچه را هم حذف کند (Phase 6).

### نحوه تست Phase 5

1. یک بازی جدید بسازید و ۲ تا ۳ دور با ترکیب‌های مختلف (موفق/ناموفق، کوت/عادی، خواننده گروه ۱ یا ۲) ثبت کنید.
2. در صفحه بازی، «مشاهده تاریخچه» را بزنید.
3. بررسی کنید:
   - دورها به ترتیب از دور ۱ به بعد نمایش داده شوند.
   - هر کارت شامل: شماره دور، گروه خواننده، مقدار خواندن، نتیجه، کوت، امتیاز/جریمه اعمال‌شده و اینکه به کدام گروه تعلق گرفته، و امتیاز هر دو گروه قبل و بعد از آن دور باشد.
   - اعداد «قبل ← بعد» با آنچه در صفحه بازی می‌بینید هم‌خوانی داشته باشد.
4. بدون ثبت هیچ دوری وارد تاریخچه شوید → پیام «هنوز دوری ثبت نشده» را ببینید.
5. به صفحه بازی برگردید و بررسی کنید «آخرین دور ثبت‌شده» با آخرین دوری که ثبت کردید مطابقت داشته باشد.

## آماده برای تأیید

Phase 5 را تست کنید؛ پس از تأیید شما، Phase 6 (Undo: حذف آخرین دور، بازگرداندن امتیاز، Dialog تأیید، به‌روزرسانی فوری UI) شروع می‌شود.

## Phase 6 — Undo آخرین دور

**تغییرات:**

- `GameViewModel.undoLastRound()` اضافه شد: آخرین دور را (بر اساس `roundNumber`) از تاریخچه پیدا می‌کند، امتیاز هر دو گروه را دقیقاً به همان مقداری که در `teamOneScoreBefore` / `teamTwoScoreBefore` آن دور ذخیره شده بود برمی‌گرداند، `currentRoundNumber` را هم به شماره همان دور برمی‌گرداند (تا دور بعدی که ثبت شود همان شماره را بگیرد)، و رکورد آن دور را از تاریخچه حذف می‌کند. اگر هیچ دوری ثبت نشده باشد، کاری انجام نمی‌شود.
- `GameScreen` اکنون قبل از فراخوانی واقعی Undo، طبق بخش ۱۵ مشخصات، یک `ConfirmDialog` با پیام «آیا مطمئن هستید؟ آخرین دور حذف خواهد شد.» نشان می‌دهد. فقط با زدن «بله، حذف کن» عملیات واقعی انجام می‌شود؛ «انصراف» فقط Dialog را می‌بندد.
- دکمه «لغو آخرین دور» تا وقتی هیچ دوری ثبت نشده باشد غیرفعال است.
- چون UI مستقیماً از `StateFlow` گیم و تاریخچه می‌خواند، امتیازها و «آخرین دور ثبت‌شده» بلافاصله بعد از Undo به‌روزرسانی می‌شوند — نیازی به رفرش دستی نیست.

**در این فاز عمداً پیاده‌سازی نشده:**
- ذخیره دائمی Undo در Database (Room هنوز در Phase 7 اضافه می‌شود؛ فعلاً همه‌چیز در حافظه است پس با بستن برنامه، هم بازی و هم تاریخچه از بین می‌رود — این طبیعی است و در Phase 7 حل می‌شود).

### نحوه تست Phase 6

1. یک بازی جدید بسازید. «لغو آخرین دور» باید غیرفعال باشد (هنوز دوری ثبت نشده).
2. یک دور ثبت کنید (مثلاً گروه A، مقدار ۷، موفق). امتیاز گروه A باید ۷ شود.
3. «لغو آخرین دور» را بزنید → Dialog تأیید با پیام «آیا مطمئن هستید؟ آخرین دور حذف خواهد شد.» باید نمایش داده شود.
4. «انصراف» بزنید → امتیاز باید همچنان ۷ بماند و هیچ تغییری رخ ندهد.
5. دوباره «لغو آخرین دور» بزنید و این‌بار «بله، حذف کن» را بزنید → امتیاز گروه A باید به ۰ برگردد، «دور فعلی» باید به ۱ برگردد، و «لغو آخرین دور» دوباره غیرفعال شود (چون تاریخچه خالی شده).
6. وارد «مشاهده تاریخچه» شوید → باید خالی باشد («هنوز دوری ثبت نشده»).
7. چند دور پشت‌سرهم ثبت کنید (مثلاً ۳ دور)، فقط آخرین دور را Undo کنید، و بررسی کنید دو دور اول دست‌نخورده در تاریخچه باقی بمانند و امتیاز دقیقاً به حالت بعد از دور دوم برگردد.

## Phase 7 — Room Database

**فایل‌های جدید:**

```
app/src/main/java/com/abusteh/shomar/data/
├── entity/
│   ├── GameEntity.kt      ← جدول games (+ enum GameStatus)
│   └── RoundEntity.kt     ← جدول rounds (با ForeignKey CASCADE به games)
├── database/
│   ├── GameDao.kt
│   ├── RoundDao.kt
│   └── AppDatabase.kt     ← تعریف Room Database + singleton
└── repository/
    └── GameRepository.kt  ← تنها نقطه دسترسی به Database برای بقیه برنامه
```

**تغییرات مهم:**

- `Game` (مدل دامنه) حالا یک فیلد `id: Long?` دارد — بعد از ذخیره در Room مقداردهی می‌شود.
- `GameViewModel` اکنون `GameRepository` را به‌عنوان وابستگی می‌گیرد (نه فقط یک کلاس بدون‌پارامتر) و همه عملیات را از طریق Coroutine (`viewModelScope.launch`) و Repository انجام می‌دهد:
  - `startNewGame` → `repository.createGame(...)` یک ردیف واقعی در جدول `games` می‌سازد.
  - `registerRound` → دور هم در جدول `rounds` ذخیره می‌شود و هم امتیاز جدید در `games` به‌روزرسانی می‌شود.
  - `undoLastRound` → رکورد دور از Database واقعاً حذف می‌شود و امتیاز بازی هم در Database برمی‌گردد.
- `MainActivity` اکنون `AppDatabase` و `GameRepository` را (با `remember`) می‌سازد و از طریق یک `viewModelFactory` به `GameViewModel` تزریق می‌کند.
- به `app/build.gradle.kts` افزونه KSP و وابستگی‌های Room (`room-runtime`, `room-ktx`, `room-compiler`) اضافه شد.

**معماری لایه Data (طبق بخش ۱۸ و ۲۱ مشخصات):**

```
ViewModel → GameRepository → GameDao / RoundDao → Room (SQLite)
```

ViewModel هرگز مستقیماً با `GameDao`/`RoundDao` یا Entityها کار نمی‌کند؛ فقط مدل‌های دامنه (`Game`, `Round`) را می‌بیند. نگاشت Entity↔Domain کاملاً داخل `GameRepository` انجام می‌شود (توابع خصوصی `toEntity()` / `toDomain()`).

**نکات طراحی برای فازهای بعدی:**
- `GameStatus` (`IN_PROGRESS` / `FINISHED`) از الان در Entity هست تا Phase 9 (پایان بازی) بتواند بدون تغییر Schema، وضعیت و برنده را ثبت کند.
- `GameDao.getLatestGameByStatus(...)` و `GameRepository.getInProgressGame()` از الان آماده‌اند تا «ادامه بازی» در Phase 8 مستقیماً از آن‌ها استفاده کند.
- حذف یک `GameEntity` به‌خاطر `ForeignKey(onDelete = CASCADE)` باعث حذف خودکار همه دورهای مرتبط می‌شود — برای «حذف تاریخچه» در Phase 11 آماده است.

**در این فاز عمداً پیاده‌سازی نشده:**
- UI «ادامه بازی» (Phase 8) — داده الان persist می‌شود ولی هنوز راهی برای بازیابی آن در رابط کاربری نیست.
- علامت‌گذاری بازی به‌عنوان `FINISHED` و ثبت برنده (Phase 9).

### نحوه تست Phase 7

از آنجا که داده حالا واقعاً روی دیسک (SQLite) ذخیره می‌شود، بهترین تست «کشتن و بازکردن مجدد برنامه» است:

1. یک بازی جدید بسازید و ۲-۳ دور ثبت کنید.
2. برنامه را کامل ببندید (نه فقط Recents؛ از تنظیمات Android یا Force Stop استفاده کنید تا مطمئن شوید پردازش واقعاً از بین رفته).
3. برنامه را دوباره باز کنید. طبیعی است که چون UI «ادامه بازی» هنوز در Phase 8 ساخته نشده، با صفحه اصلی خالی روبه‌رو می‌شوید — این مرحله فقط تأیید می‌کند برنامه کرش نمی‌کند.
4. برای تأیید واقعی ذخیره‌سازی، از Android Studio → **App Inspection → Database Inspector** استفاده کنید: در حین اجرای برنامه به دیتابیس `abusteh_shomar.db` وصل شوید و جدول‌های `games` و `rounds` را ببینید — باید بازی و دورهایی که ثبت کردید آنجا باشند، حتی بعد از بستن و بازکردن برنامه.
5. یک Undo انجام دهید و در Database Inspector بررسی کنید که ردیف مربوط به آن دور واقعاً از جدول `rounds` حذف شده و امتیاز در جدول `games` هم به‌روزرسانی شده باشد.
6. مطمئن شوید ثبت دور و Undo هنوز بدون تأخیر محسوس کار می‌کنند (بخش ۲۵ مشخصات — Room روی Coroutine اجرا می‌شود، نه Main Thread).

Phase 7 را تست کنید؛ پس از تأیید شما، Phase 8 (ادامه بازی: پیدا کردن بازی نیمه‌تمام از Database، فعال‌سازی دکمه «ادامه بازی» در صفحه اصلی، و بازیابی دقیق وضعیت قبلی) شروع می‌شود.

## Phase 8 — ادامه بازی

**تغییرات:**

- `GameViewModel.refreshSavedGameStatus()` اضافه شد: با `repository.getInProgressGame()` بررسی می‌کند آیا بازی نیمه‌تمامی در Database هست، و نتیجه را در `StateFlow<Boolean> hasSavedGame` می‌گذارد.
- `GameViewModel.continueGame()` اضافه شد: آخرین بازی نیمه‌تمام و **تمام دورهای ذخیره‌شده آن** را از Database می‌خواند و دقیقاً همان وضعیت (امتیاز هر دو گروه + کل تاریخچه دورها) را در ViewModel می‌نشاند — طبق بخش ۸ مشخصات («دقیقاً وضعیت قبلی بازی بازیابی شود»).
  - نکته فنی: شماره دور فعلی (`currentRoundNumber`) هیچ‌وقت مستقیم در Database ذخیره نشده (چون همیشه برابر «تعداد دورهای ثبت‌شده + ۱» است)؛ در `continueGame()` از روی تعداد دورهای بازیابی‌شده بازسازی می‌شود، پس رفتار «ثبت دور بعدی» بعد از ادامه بازی دقیقاً مثل قبل از بستن برنامه است.
- `MainActivity`: هر بار صفحه اصلی نمایش داده می‌شود (`LaunchedEffect(Unit)`)، `refreshSavedGameStatus()` صدا زده می‌شود تا دکمه «ادامه بازی» همیشه با وضعیت واقعی Database هماهنگ باشد. با زدن این دکمه، `continueGame()` صدا زده و مستقیم به صفحه بازی می‌رود.

**در این فاز عمداً پیاده‌سازی نشده:**
- اگر بیش از یک بازی نیمه‌تمام در Database باشد (که در جریان عادی برنامه نباید پیش بیاید، چون شروع بازی جدید همیشه باید بازی قبلی را ببندد)، `continueGame()` فقط جدیدترین آن‌ها را برمی‌گرداند. رسمی‌کردن این قانون (بستن بازی‌های قبلی هنگام شروع بازی جدید) بخشی از Phase 9 است، جایی که وضعیت `FINISHED` روی Entity واقعاً استفاده می‌شود.

### نحوه تست Phase 8

1. یک بازی جدید بسازید و ۲-۳ دور با ترکیب‌های مختلف ثبت کنید (مثلاً امتیاز نهایی A=۱۹، B=۱۰).
2. برنامه را کامل ببندید (Force Stop یا حذف از Recents + مطمئن شدن که پردازش از بین رفته).
3. برنامه را دوباره باز کنید. حالا در صفحه اصلی، دکمه «ادامه بازی» باید **فعال** باشد (بر خلاف حالت شروع تازه برنامه که این دکمه غیرفعال بود).
4. «ادامه بازی» را بزنید. بررسی کنید:
   - نام هر دو گروه دقیقاً همان‌هایی باشد که وارد کرده بودید.
   - امتیاز هر دو گروه دقیقاً با قبل از بستن برنامه یکسان باشد (A=۱۹، B=۱۰ در این مثال).
   - وارد «مشاهده تاریخچه» شوید — همه دورهایی که قبل از بستن برنامه ثبت کرده بودید باید کامل آنجا باشند.
5. یک دور جدید ثبت کنید و بررسی کنید شماره دور درست ادامه پیدا کند (نه اینکه از ۱ شروع شود).
6. یک بار «لغو آخرین دور» را امتحان کنید تا مطمئن شوید بعد از ادامه بازی هم Undo درست کار می‌کند.
7. از صفحه اصلی یک «شروع بازی جدید» بسازید (بدون بستن این بازی نیمه‌تمام قبلی) و دوباره برنامه را ببندید و باز کنید — «ادامه بازی» باید این‌بار آخرین (جدیدترین) بازی را باز کند.

Phase 8 را تست کنید؛ پس از تأیید شما، Phase 9 (پایان بازی: تشخیص ۶۲ امتیاز، نمایش برنده، علامت‌گذاری بازی به‌عنوان FINISHED در Database، دکمه «بازی جدید») شروع می‌شود.

## Phase 9 — پایان بازی

**تغییرات:**

- `GameRepository.finishGame(gameId, winnerTeamName)` اضافه شد: وضعیت بازی در Database را به `FINISHED` تغییر می‌دهد، نام گروه برنده و زمان پایان را ثبت می‌کند (بدون دست‌زدن به امتیازهای نهایی که قبلاً ذخیره شده‌اند).
- `GameViewModel.registerRound(...)`:
  - قبل از ثبت دور، اگر بازی از قبل برنده داشته باشد (حالت دفاعی، طبق بخش ۲۶ مشخصات)، هیچ کاری نمی‌کند.
  - بعد از اعمال دور، با `ScoringEngine.winner(...)` بررسی می‌کند آیا کسی به ۶۲ رسیده؛ اگر بله، `repository.finishGame(...)` را هم صدا می‌زند.
- `GameScreen`: در ابتدای Composable، برنده را با `ScoringEngine.winner(game)` بررسی می‌کند. اگر برنده‌ای وجود داشته باشد، به‌جای صفحه معمولی بازی، `GameOverContent` نمایش داده می‌شود — دقیقاً طبق بخش ۱۶ مشخصات: «🏆 بازی تمام شد»، نام برنده، امتیاز نهایی هر دو گروه، و دکمه «بازی جدید».
- دکمه «بازی جدید» کاربر را به صفحه «شروع بازی جدید» می‌برد (همان صفحه‌ای که از منوی اصلی هم در دسترس است) و پشته Navigation تا صفحه اصلی پاک می‌شود.

**نکته مهم درباره یکتایی بازی نیمه‌تمام:** حالا که بازی برنده‌دار در Database به `FINISHED` تغییر وضعیت می‌دهد، مشکلی که در پایان Phase 8 اشاره شد خودش حل می‌شود: `getInProgressGame()` دیگر این بازی را برنمی‌گرداند، پس «ادامه بازی» همیشه فقط بازی‌های واقعاً ناتمام را پیشنهاد می‌دهد.

**در این فاز عمداً پیاده‌سازی نشده:**
- تاریخچه بازی‌های قبلی (Phase 10) — الان که بازی‌ها با وضعیت `FINISHED` و `winner` در Database ذخیره می‌شوند، Phase 10 می‌تواند مستقیم از همین داده استفاده کند.

### نحوه تست Phase 9

1. یک بازی جدید بسازید.
2. چند دور ثبت کنید تا امتیاز یکی از گروه‌ها به ۶۲ یا بیشتر برسد (مثلاً با ثبت دورهای موفق پیاپی برای همان گروه).
3. بلافاصله بعد از دوری که امتیاز را به ۶۲ یا بیشتر می‌رساند، باید صفحه پایان بازی نمایش داده شود: «🏆 بازی تمام شد»، نام گروه برنده، و امتیاز نهایی هر دو گروه.
4. بررسی کنید هیچ‌کدام از دکمه‌های «ثبت دور جدید» یا «لغو آخرین دور» در این صفحه در دسترس نباشند (چون کل صفحه با محتوای پایان بازی جایگزین شده).
5. «بازی جدید» را بزنید → باید به صفحه ورود نام گروه‌ها بروید و بتوانید یک بازی کاملاً تازه شروع کنید.
6. با Database Inspector بررسی کنید ردیف بازی تمام‌شده در جدول `games` مقدار `status = FINISHED`، `winner` برابر نام گروه برنده، و `endDate` مقداردهی‌شده داشته باشد.
7. برنامه را ببندید و باز کنید — چون بازی قبلی حالا `FINISHED` است، دکمه «ادامه بازی» در صفحه اصلی باید غیرفعال باشد (مگر اینکه بازی جدید دیگری نیمه‌تمام مانده باشد).
8. یک سناریوی مرزی را هم امتحان کنید: دوری که هر دو گروه را همزمان به بالای ۶۲ نمی‌رساند طبیعتاً پیش نمی‌آید (چون هر دور فقط امتیاز یک گروه را تغییر می‌دهد)، پس این حالت نیازی به تست دستی ندارد — قبلاً در `AbusteRulesTest` پوشش داده شده.

**تغییرات مهم:**

- `GameRepository.getFinishedGames()` اضافه شد: همه ردیف‌های با `status = FINISHED` را می‌خواند و به `GameSummary` تبدیل می‌کند (شامل نام گروه‌ها، امتیاز نهایی، نام برنده و تاریخ).
- `HistoryViewModel` (طبق نام‌گذاری معماری اصلی در بخش ۱۸) جدا از `GameViewModel` ساخته شد چون هیچ ارتباطی با بازی *جاری* ندارد؛ فقط بازی‌های *تمام‌شده* را می‌خواند.
- `ui/screens/HistoryScreen.kt` (که در Phase 5 برای تاریخچه دورهای بازی جاری ساخته بودیم) بازطراحی شد تا به‌جای گرفتن یک `Game` زنده، فقط نام دو گروه را بگیرد — همین باعث شد بتوانیم دقیقاً همان کامپوننت را برای «جزئیات دورهای یک بازی قدیمی» هم دوباره استفاده کنیم، بدون کد تکراری.
- دکمه «تاریخچه بازی‌ها» در صفحه اصلی حالا واقعاً وصل است.

**جریان کار:**
1. صفحه اصلی → «تاریخچه بازی‌ها» → لیست بازی‌های تمام‌شده (هر کارت: `گروه A × گروه B`, `۶۲ - ۴۸`, `برنده: گروه A`, `تاریخ: ...`، جدیدترین اول).
2. لمس هر کارت → `HistoryViewModel.selectGame(...)` دورهای همان بازی را از Database می‌خواند → صفحه جزئیات (همان `HistoryScreen` با کارت‌های آشنای هر دور) باز می‌شود.

**نکته درباره تاریخ:** فعلاً تاریخ با تقویم میلادی عددی (`yyyy/MM/dd HH:mm`) نمایش داده می‌شود — این فرمت مستقل از Locale و همیشه درست است. تبدیل به تقویم شمسی (جلالی) می‌تواند در Phase 12 (طراحی نهایی UI) اضافه شود؛ چون این یک تصمیم ظاهری است نه یک قانون بازی، طبق بخش ۳۳ آن را حدس نزدم و همین رفتار امن پیش‌فرض را انتخاب کردم — اگر مایلید همین الان تقویم شمسی اضافه شود بگویید.

**در این فاز عمداً پیاده‌سازی نشده:**
- حذف یک بازی خاص از تاریخچه (فقط «حذف کل تاریخچه» در تنظیمات، بخش ۱۱، در Phase 11 اضافه می‌شود).

### نحوه تست Phase 10

1. حداقل دو بازی را کامل تا پایان (رسیدن به ۶۲) بازی کنید تا دو ردیف `FINISHED` در Database داشته باشید.
2. از صفحه اصلی وارد «تاریخچه بازی‌ها» شوید.

## Phase 11 — تنظیمات

**فایل‌های جدید:**

```
app/src/main/java/com/abusteh/shomar/
├── data/settings/AppSettings.kt     ← تنظیمات ساده روی SharedPreferences (نه Room)
├── viewmodel/SettingsViewModel.kt   ← طبق نام‌گذاری معماری اصلی
└── ui/screens/SettingsScreen.kt     ← صفحه تنظیمات
```

**تصمیم طراحی — چرا SharedPreferences و نه Room:** تنظیم «تأیید ثبت دور» یک ترجیح کلی برنامه است، نه داده بازی؛ طبق بخش ۱۷ مشخصات Room فقط برای `Game` و `Round` در نظر گرفته شده بود، پس این تنظیم را جدا و سبک با SharedPreferences نگه داشتم.

**پنج بخش تنظیمات (دقیقاً طبق بخش ۱۱ مشخصات):**

1. **تغییر نام گروه‌ها** — اگر بازی‌ای در حال انجام باشد، دو فیلد با نام فعلی گروه‌ها پر می‌شوند؛ با «ذخیره نام‌ها» هم در حافظه و هم در Database به‌روزرسانی می‌شود (`GameViewModel.renameTeams(...)`، و `GameRepository.updateGameState(...)` که حالا نام‌ها را هم ذخیره می‌کند، نه فقط امتیاز). اگر بازی فعالی نباشد، پیام «در حال حاضر بازی فعالی وجود ندارد» نمایش داده می‌شود.
2. **بازی جدید** — دکمه میان‌بر به همان جریان «شروع بازی جدید».
3. **تأیید قبل از ثبت دور** — یک Switch که مقدارش در `AppSettings` ذخیره می‌شود. `RoundScreen` اکنون پارامتر `confirmBeforeRegister` می‌گیرد: اگر خاموش باشد، با زدن «ثبت دور» بدون نمایش Dialog، بلافاصله دور ثبت می‌شود.
4. **حذف تاریخچه** — با Dialog تأیید (چون غیرقابل‌بازگشت است، طبق بخش ۲۶ مشخصات). `GameRepository.deleteFinishedGamesHistory()` فقط بازی‌های **تمام‌شده** (و دورهای‌شان) را حذف می‌کند.
5. **اطلاعات برنامه** — نام برنامه و شماره نسخه (از `BuildConfig.VERSION_NAME`؛ برای همین `buildConfig = true` به Gradle اضافه شد).

**یک تصمیم که باید بدانید (نه یک قانون بازی، پس رأساً تصمیم گرفتم ولی صادقانه می‌گویم):** «حذف تاریخچه» در مشخصات دقیق نگفته بود آیا باید بازی نیمه‌تمام فعلی را هم پاک کند یا نه. من فقط بازی‌های **تمام‌شده** را حذف می‌کنم و به بازی‌ای که کاربر شاید همین الان وسط آن باشد دست نمی‌زنم — به نظرم منطقی‌ترین و امن‌ترین برداشت از «حذف تاریخچه» همین است. اگر منظورتان پاک کردن کامل همه‌چیز (از جمله بازی جاری) بود، بگویید تا اصلاح کنم.

**در این فاز عمداً پیاده‌سازی نشده:**
- هیچ‌چیز خاصی از بخش ۱۱ باقی نمانده — این آخرین آیتم فهرست ویژگی‌های اصلی برنامه بود (پیش از Phase 12 طراحی نهایی، Phase 13 تست کامل، و Phase 14 خروجی APK).

بخش ۲۷ مشخصات اصلی شما، برای «تست ۴: ثبت دور ناموفق برای گروه اول» نوشته بود: *«اطمینان حاصل شود جریمه برای گروه اول اعمال شده است.»* این متن از **قبل از** اصلاحی است که خودتان در گفتگو دادید (که جریمه باید به گروه **حریف** برود، نه به خود گروه ناموفق). پیاده‌سازی فعلی طبق تأیید صریح شما در گفتگو (گزینه B) درست است — جریمه به حریف می‌رود — و این دقیقاً همان چیزی است که `failedRoundByTeamOneAddsPenaltyToTeamTwo` در `ScoringEngineTest` تست و تأیید می‌کند. متن قدیمی تست در بخش ۲۷ را نادیده گرفتم چون با تأیید صریح بعدی شما در تناقض است؛ فقط برای شفافیت این‌جا ذکر کردم.

### مشکل واقعی پیدا‌شده و رفع‌شده: مدیریت خطا (بخش ۲۶ مشخصات)

مرور کد نشان داد عملیات‌های Database (شروع بازی، ثبت دور، Undo، ادامه بازی، تغییر نام گروه‌ها، حذف تاریخچه) هیچ `try/catch`ی نداشتند. طبق بخش ۲۶ مشخصات («خطاها نباید باعث Crash شدن برنامه شوند. پیام خطا برای کاربر باید ساده و فارسی باشد»)، این یک نقص واقعی بود. رفع شد:

- هر سه ViewModel (`GameViewModel`، `HistoryViewModel`، `SettingsViewModel`) حالا یک `errorMessage: StateFlow<String?>` و تابع `clearError()` دارند.
- هر عملیات Database داخل `try/catch` اجرا می‌شود؛ در صورت خطا، یک پیام ساده فارسی (مثلاً «ثبت دور با مشکل مواجه شد. دوباره تلاش کنید.») در این StateFlow قرار می‌گیرد، نه جزئیات فنی خطا.
- `MainActivity` حالا یک `Scaffold` با `SnackbarHost` مشترک دور کل Navigation دارد و هر سه `errorMessage` را observe می‌کند؛ با بروز خطا، یک Snackbar کوتاه نمایش داده و بعد پاک می‌شود.

### مشکلات بررسی‌شده که پیدا نشدند
- **Rotation:** چون `MainActivity` از `android:screenOrientation="portrait"` استفاده می‌کند (طبق Manifest از Phase 1)، چرخش صفحه اصلاً رخ نمی‌دهد؛ ریسک از دست رفتن state با چرخش منتفی است.
- **از دست رفتن اطلاعات:** چون همه چیز فوراً (نه batch) در Room ذخیره می‌شود، حتی خروج ناگهانی از برنامه داده را از دست نمی‌دهد.
- **مشکل Database:** با Database Inspector (طبق تست‌های Phase 7-9) تأیید شده بود که schema و روابط CASCADE درست کار می‌کنند.

## Phase 14 — خروجی APK (فاز پایانی)

**محدودیت صادقانه:** این محیط (جایی که من کد را می‌نویسم) نه Android SDK نصب دارد و نه به `dl.google.com` (مخزن Maven گوگل، جایی که AGP و کتابخانه‌های AndroidX/Compose از آن دانلود می‌شوند) دسترسی دارد. پس نمی‌توانم خودم واقعاً `assembleDebug` را اینجا اجرا کنم و یک فایل APK واقعی تحویل بدهم. کاری که **در همین فاز واقعاً انجام دادم**، نه فقط توضیح:

- کل پروژه (۲۹ فایل Kotlin) را از نظر **تعادل آکولاد/پرانتز** بررسی کردم — همه فایل‌ها تمیز هستند.
- هر `R.string.*` استفاده‌شده در کد (۶۹ مورد) را با تعریف‌شده‌ها در `strings.xml` مقایسه کردم — دقیقاً یکی‌به‌یک تطبیق دارند، هیچ رشته گم‌شده‌ای نیست.
- هر `R.font.*` و هر Composable صفحه که در `MainActivity` صدا زده می‌شود را با فایل‌های واقعی موجود مقابله کردم — همه درست هستند.
- نسخه‌های Kotlin (۱.۹.۲۴) / Compose Compiler (۱.۵.۱۴) / KSP (۱.۹.۲۴-۱.۰.۲۰) را با جدول سازگاری رسمی JetBrains چک کردم — سازگارند.
- **`gradlew`، `gradlew.bat` و `gradle-wrapper.jar` واقعی** (نسخه Gradle 8.7، سازگار با AGP 8.5.2) را به پروژه اضافه کردم — قبلاً این پروژه فاقد Wrapper واقعی بود و کاربر باید Android Studio را برای ساخت آن باز می‌کرد؛ از الان پروژه کاملاً از خط فرمان هم قابل build است، بدون نیاز به باز کردن Android Studio.

### ساخت Debug APK

```bash
cd AbustehShomar
./gradlew assembleDebug
```

(ویندوز: `gradlew.bat assembleDebug`)

مسیر خروجی:
```
app/build/outputs/apk/debug/app-debug.apk
```

### ساخت Release APK

Release APK باید امضا (sign) شود. اگر فقط می‌خواهید روی گوشی خودتان نصب کنید (نه انتشار در Play Store)، ساده‌ترین راه:

1. یک keystore بسازید (یک‌بار کافی است):
   ```bash
   keytool -genkeypair -v -keystore abusteh-release.keystore -alias abusteh -keyalg RSA -keysize 2048 -validity 10000
   ```
2. در `app/build.gradle.kts`، داخل بلوک `android { }`، یک `signingConfigs` اضافه کنید و آن را به `buildTypes.release` وصل کنید (چون این کار نیاز به وارد کردن رمز عبور شخصی شما دارد، عمداً آن را داخل کد آماده ننوشتم — بهتر است خودتان این مقادیر حساس را وارد کنید، ترجیحاً از طریق `gradle.properties` محلی که در Git کامیت نمی‌شود).
3. سپس:
   ```bash
   ./gradlew assembleRelease
   ```
   خروجی: `app/build/outputs/apk/release/app-release.apk`

### نصب روی گوشی

```bash
adb install app/build/outputs/apk/debug/app-debug.apk
```
یا فایل APK را مستقیم به گوشی منتقل کرده و از آنجا نصب کنید (نیاز به فعال کردن «نصب از منابع ناشناس» دارد).

### توصیه نهایی

چون من نتوانستم واقعاً این build را در این محیط اجرا کنم، **لطفاً همین یک بار `./gradlew assembleDebug` را روی سیستم خودتان (با Android Studio نصب‌شده) اجرا کنید** تا از صحت کامل پروژه مطمئن شوید. اگر خطایی گرفتید (مثلاً به‌خاطر نسخه JDK متفاوت یا تنظیمات محلی)، پیامش را برایم بفرستید تا رفعش کنم.
